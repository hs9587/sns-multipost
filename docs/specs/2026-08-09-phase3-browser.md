# Phase 3 ブラウザ投稿

- 日付: 2026-08-09
- 状態: mixi2ポスト、mixiつぶやき、Jotter公開テキスト／単画像投稿の実装・実投稿確認完了

## 方針

ブラウザ投稿は、公式APIが使えない投稿先に限って採用する。サービスごとに
利用条件、ログイン維持、投稿画面のDOM、画像上限、投稿完了判定を先に確認し、
失敗時はジョブと同じ識別子でスクリーンショットを保存できる構成にする。

## 暫定優先順

1. mixi2: 公式にChrome対応のブラウザ版と、テキスト・画像最大4件の投稿を提供。
   最初の画面調査対象とする
2. mixi: PCブラウザの「つぶやき」を対象とする。本文150文字、画像は先頭1枚、JPEGまたはPNGで
   5MBまで。公開範囲を選択して「つぶやく」で送信する。日記投稿とタイトル欄は対象外
3. Jotter.me: セーブポイント復元、本人確認、公開テキストと先頭画像1枚の投稿、投稿URL確認まで
   実装・実投稿確認済み。画像投稿は専用Browser IDとDEN残高を事前確認する
4. Instagram: 既存アカウントは非公開の個人アカウント。公式投稿APIに必要なプロアカウントへ
   切り替えると承認待ちフォローリクエストが自動承認されるため、切り替えない。ブラウザ自動化も
   行わず、本文と画像を用意して本人が投稿する手動引き渡しとする
5. Facebook個人プロフィール: 公式投稿APIの対象外で、Meta利用規約上も許可のないブラウザ自動
   アクセスは採用しない。Instagramと同じ手動引き渡しとする

Xは公式Automation rulesがWebサイトのスクリプト操作を禁止しているため、
ブラウザ自動投稿の対象外とする。APIクレジットを購入しない間は、本文をクリップボードへ
用意して公式Webを開き、利用者が投稿する手動引き渡しとする。X、Instagram、Facebookで
共通利用でき、外部投稿の完了を利用者が明示的に確認する仕組みとする。ただし、外出中の
自動実行を優先するため、手動引き渡しの実装はThreads画像投稿と運用強化より後で再検討する。

## Jotter.me 実装結果

Jotter.meのセーブポイントURLは認証情報として扱い、Git管理外の `config.yml` にのみ保存する。
Jotterの暗号処理中にFerrumから画面を操作すると処理が停止するため、まず専用プロファイルの
素のChromeでセーブポイントを開き、30秒待ってからリモートデバッグ接続する。接続後はJotterの
タブを選択し、walletとユーザー画像の表示、設定画面の表示名が `account_name` と一致することを
確認する。復元成功後もURLのhashが残るため、hashの有無だけでは失敗と判定しない。

投稿時はホームから作成画面へ進み、`textarea[name="text"]` に本文を入力する。公開範囲の
`select` は既定の下書きではなく `auth` を明示的に選び、Post後に表示されるHTML確認画面の
`Ok` を押す。新しい公開投稿URLを取得できた場合だけ成功とする。2026-08-09に公開テキスト投稿と
別ブラウザからの閲覧を確認した。例外時は他のブラウザ投稿先と同様、ジョブ識別子に対応する
スクリーンショットを `failed/` に保存する。

画像投稿は2026-08-15に先頭1枚で実地確認した。専用ChromeのBrowser IDが再起動後も同一であること、
別ブラウザから振り替えたDENが未検証へ入り、検証要求後に利用可能になることも確認した。
画像選択後に表示される実費を読み取り、利用可能DENが足りない場合は送信しない。
複数画像は途中でDEN状態が変わりやすいため対象外とし、常に先頭1枚へ制限する。
ウォレットの詳細と運用手順は `2026-08-15-jotter-image-den.md` に分離した。

## mixi2 最初の確認

ログインはMIXI IDのメールアドレス、メールで届く認証コード、利用ID選択の3段階。
メールアドレスや認証コード自体は設定・文書・ログへ保存しない。

ログイン後のホームと投稿フォームを、外部投稿せずに確認した結果:

- ホーム右上はアクセシブル名 `ポスト` のbutton
- 投稿画面はアクセシブル名 `新規ポスト作成` のdialog
- 本文欄は `.tiptap.ProseMirror[contenteditable="true"]`
- 送信は `button[type="submit"][aria-label="送信"]`。本文が空ならdisabled
- 添付は `input[type="file"]`。JPEG / PNG / WebP / GIF / MP4 / QuickTime対応。
  実行環境によりmultiple属性が無いため、最大4枚を1枚ずつ追加する
- 通常ポストは約150文字枠。公開先は公開、プロフィールのみ、コミュニティから選ぶ

CLI実行用には `bin/browser_login mixi2` で専用Chromeを開き、ログイン状態を
Git管理外の `state/browser/mixi2` に保存する。次はこのプロファイルをFerrumから開き、
ログイン保持と投稿画面到達を確認する。Ferrumは既定でincognitoコンテキストを作るため、
永続プロファイル利用時は `incognito: false` を必ず指定する。またFerrum 0.17.2は
トップレベルの `user_data_dir:` を認識しないため、`browser_options` の
`user-data-dir` でChrome起動引数を上書きする。

`bin/mixi2_smoke` により、専用プロファイルのログイン保持、ホーム到達、投稿画面の
本文欄・送信ボタン・メディア入力を確認し、投稿せず閉じるところまで成功した。
`Poster::Mixi2` は本文を150 graphemeへ収め、画像を先頭4枚に制限してFerrumへ渡す。
`bin/post` が作成したmixi2ジョブを `bin/run_queue` で処理し、投稿URLが返ることと、
別ブラウザから公開投稿を閲覧できることを確認済み。実際の投稿URLやログイン情報は
文書・Gitへ保存しない。

Fedibird監視からの初回画像付き投稿では本文だけが公開された。調査の結果、非表示のレスポンシブ用
要素を選ぶ可能性を除くため、本文欄・メディア入力・送信ボタンを表示中の投稿ダイアログ内へ限定した。
また、従来の「最大30秒待機」は通信が待機中なら即終了し、実際には1秒しか保持していなかった。
画像プレビューを確認後、投稿フォームを実際に30秒保持してから送信するよう修正し、画像付き公開投稿を
別ブラウザで確認した。投稿画面が閉じただけでは成功とせず、新しい投稿URLの検出を必須とした。
送信後にも「画像をアップロードしています」が表示される場合があるため、画像付き投稿ではこの表示が
消えるまで最大120秒Chromeを保持する。その後も新規URLを最大120秒待ち、見つからなければホームを
再読込みしてもう一度確認する。アップロード中にChromeを閉じて投稿が失われることを防ぐ。
2026-08-17に、失敗時画面で送信後の画像アップロード表示が残っていた事例へこの対策を適用し、
同じ失敗ジョブの再試行で画像付き投稿と投稿URLを確認した。

mixi2投稿が例外終了した場合は、Chromeを閉じる前に表示中の画面を
`failed/<ジョブ識別子>.png` へ保存する。スクリーンショット取得自体の失敗は元の投稿エラーを
上書きしない。成功時には保存せず、画像はGit管理外とする。

2026-08-09時点の開発環境では、`state/browser` 約479MB、`state/media` 約43MB、ログ約0.14MB、
完了ジョブ約0.04MBで、直ちにローテーションは不要。実稼働後に増加傾向を確認して保持期間と
容量上限を決める。Chromeプロファイルと画像が主な監視対象になる。

## mixiつぶやきの確認

mixiは日記ではなく、PCホームの「つぶやき」を対象とする。ログインはメールアドレスと
パスワードの入力後、中間画面の「続行する」を押してホームへ進む。認証情報自体は文書・設定・
ログへ保存しない。`bin/browser_login mixi` で専用Chromeを開き、Git管理外の
`state/browser/mixi` にログイン状態を保持する。

投稿せずにDOMを確認した結果:

- 本文は `#voiceComment`。上限150文字
- 写真追加は title が `写真を追加` のリンク。開くと `input[type=file][name=photo]` が現れる
- 画像は先頭1枚、JPEGまたはPNG、5MBまで
- 送信は `#voicePostSubmit`
- 公開範囲はフォームの現在値を維持する。確認時の既定値は「全体に公開」
- 投稿本文は `p.description`、詳細URLは `view_voice.pl` のリンクから確認できる

`bin/mixi_smoke` でログイン、本文欄、送信、写真入力を投稿せず確認できる。
テキストのみとPNG画像1枚の公開つぶやきを実投稿し、別の読込で本文・画像・詳細URLを確認した。
画像付き投稿は反映に30秒を超える場合があるため最大60秒待ち、見つからない場合は再送信せず
ホームを再読込して新規URLを確認する。例外時はmixi2と同様に `failed/<ジョブ識別子>.png` を保存する。
広告などによる画面更新で取得済みDOM要素が無効になる場合があるため、本文欄、写真追加、写真入力、
送信ボタンの操作で `NodeNotFoundError` が発生した場合は、要素を取り直して最大3回まで再試行する。
2026-08-18には要素の操作時ではなく検索時にも同じ例外が発生したため、検索と操作の両方を再試行の
対象にした。失敗画面は本文・画像を入れる前のホームであり、送信前の失敗と確認できた。
2026-08-20にも本文入力前の画面更新が連続して再現したため、本文入力、写真追加、送信はDOM要素を
Ruby側に保持せず、ページ内で検索して直ちに操作する方式へ変更した。ファイル選択だけはブラウザの
制約上DOM要素が必要なため、要素再取得を継続する。
2026-08-22には本文入力と写真欄表示の後、未選択のファイル入力が差し替わって失敗した。写真欄を
開いた後に1秒待ち、ファイル入力を最大8回・1秒間隔で取り直してから選択する。
